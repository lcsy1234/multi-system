# 果糖接收、使用记录表如何支持在线编辑

**员工直接在上传的 Excel 模板上编辑。** 打开草稿时，工作台应按这次上传的工作簿呈现标题、合并区域、表头、明细、备注和签字栏。点击可填单元格时在原位置输入，保存后重新打开和下载均使用同一版工作簿。窄屏可以横向滚动或缩放，保持原来的行列关系。

网页与下载文件都以原模板为版式基准。首期先用真实工作簿验证两条路线的保真度：嵌入工作簿编辑器，或由 React 读取实际工作表的布局和样式，仅在允许的位置叠加输入控件。选择取决于原件对照结果；多人协作是独立的选型因素。

## 当前交付与新增验收

聊天中原先列出的第四步要求展示摘要、数据预览和 Excel 下载。新增要求把员工编辑插在 Agent 填完和最终下载之间。`yq-tablehandle-system/frontend/src/main.tsx` 的结果区用普通表格展示文本，`backend/agent.go` 最多返回 20 条已写入行的预览。缺数据时，员工可能恰好看不到最需要补录的行。`backend/main.go` 提供结果下载，使用启动时创建的临时目录，尚缺报表草稿的读取、更新与持久化能力。

用户原版《果糖接收、使用记录表.xlsx》包含 28 个合并区域，工作表中没有公式。A4:P6 是三级表头，第 7 行开始填明细，底部有说明和签字区域。P 列“日结存”由 `backend/fructose.go` 按全厂数据算好后写入数值。浏览器直接改班次用量或接收量，P 列不会自行变化。其他含 `SUM` 等公式的生产日报仍需独立验收。

## 三种实现路线

| 路线 | 编辑与保存方式 | 对本项目的取舍 |
| --- | --- | --- |
| React 可编辑表单 + Gin + Excelize | 前端按原模板组织接收、储存、使用、结存区，后端校验改动并写入工作簿副本，保存新版本。Excelize 提供按 Sheet 和坐标读写数值、文本、公式及查询合并范围的接口。 | 适合模板样式范围明确的场景。须按实际文件渲染合并、行高列宽、字体、边框、填色、对齐、换行和数字格式。网页、导出和打印分别对照同一原件验收。跨窗口修改先做版本冲突提示。 [Excelize 单元格文档](https://xuri.me/excelize/en/cell.html) |
| 嵌入 ONLYOFFICE Docs | 浏览器加载编辑器，使用相同 `document.key` 的用户进入同一协作会话。Gin 作为存储服务接收回调；状态 2 表示改后可保存，6 表示强制保存，从回调 `url` 取回并持久化文件。 | 适合直接编辑多种原格式工作簿的场景，可用果糖原件先验证单人编辑及回存。需另行接入文档服务、身份权限、文件版本和业务字段保护，并拿原件验证导出。 [协作机制](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/co-editing/) · [保存协议](https://api.onlyoffice.com/docs/docs-api/usage-api/callback-handler/) |
| 飞书电子表格 / 多维表格 | 飞书电子表格适合员工在共享表格中改格、看公式；多维表格按字段和记录组织数据，可记录工厂、报表日期、负责人、状态及报表链接或附件。 | 若现场已有飞书协作习惯，可将电子表格作为协作入口，把多维表作为报表台账。须明确哪一处保存权威版本，再用原样本实测导入导出的合并区、公式与打印效果。 [飞书云文档概述](https://open.feishu.cn/document/server-docs/docs/docs-overview?lang=zh-CN) · [多维表格附件与记录](https://open.feishu.cn/document/docs/bitable-v1/faq?lang=zh-CN) |

## 建议实现顺序

1. **生成完整草稿。** Agent 完成后记录报表 ID、原模板、AI 填报副本、筛选条件、版本。读取接口返回各 Sheet 的表头、合并范围及全部适用明细行，包含可补录空格、稳定行标识、单元格坐标、原始类型、展示值和可编辑规则。用工厂与日期关联数仓记录。重复日期或缺少定位信息时显式标记，避免修改错误记录。
2. **让员工核对与补录。** 默认展示已填值，给缺项和人工修改加标识；根据字段选择数值框、日期控件、文本或检查结果下拉。汇总、表头、备注说明、既有公式、合并区域的从属格都设为只读。默认保留模板预填内容。区分“未修改”“明确清空”和数值 0。AI 查无数据仍留空；员工补录后保留人工来源。
3. **用后端规则保存。** 可新增 `PATCH /api/reports/{id}`，提交版本及少量修改。服务端依据原模板和字段定义重新判断可写范围，在当前已保存副本上按类型写值。此前用于 Agent 的“原本为空”规则不能直接用于员工纠错，因为员工要改的格子可能已有 AI 值。整批校验后原子保存文件和版本引用，失败保留前版。两个页面从同一旧版本保存时，后一次给出冲突字段并保留待提交改动。可以先用本地持久目录和 SQLite 保存版本、来源、旧值与新值。
4. **处理库存一致性。** 温度、接收人等字段可以独立修正。编辑接收量、用量时，服务端须使用期初、接收量及全厂六个班次用量重算当日 P 列，即使当前筛选只展示部分产线。若同份草稿跨天并采用连续结存，同时校正后续日期的期初和日结存。缺任一必要数值、数据断档或涉及另一张已确认报表时，显示受影响日期并要求核实。实际数仓中哪个系统有权更正历史库存，需由业务确认。首期可先开放不涉及结存联动的字段。
5. **从同一版本交付。** 保存成功后重载服务端版本、更新缺项清单和下载地址。导出请从该版本的工作簿生成，保留原模板和各 Sheet 样式。人工更正默认限于本次报表草稿；未来若需回写 MES 或数仓，另定审批、幂等及来源记录。

## 用真实模板验收

- 并排打开原 Excel 和网页草稿，对照 A4:P6 三级表头、28 个合并范围，以及 A24:P25 备注和第 26 行签字区的位置与样式。另取测试副本，更改一列列宽和一个表头底色，重新上传后网页应随新文件变化，用以验证版式来自上传文档。
- 在 G7（1 号罐温度）修改为 26.5，保存、刷新、重新进入及下载后均为数值 26.5。模拟保存失败时，页面保留待保存输入，下载仍取上个成功版本。
- 给一个查无数据且在报告范围内的明细行补录，确认缺项提醒和人工来源同步更新。清空后恢复为缺项；填 0 后应保持为有效数值。
- 修改某产线班次用量并保持其余输入固定；若增加 0.2 吨，按演示口径当日日结存应减少 0.2 吨。切换产线筛选后全厂结存应一致。跨日草稿还要核对下一日期初。
- 导出后逐项对照 28 个合并范围、三级表头、签字区、原样式和打印版式。在另一份含公式模板上对照公式文本、可写区域和 Excel 打开后的汇总结果。只看果糖原件无法验证公式保护。
- 两个页签读取同一版本，依次保存不同改动，验证后保存者获得可操作的冲突提示；若未来承诺多人实时协作，再测试同一文档的跨用户即时同步。

以上为基于当前代码、用户模板及官方接口的方案调研，验收项为后续实现的测试用例。
