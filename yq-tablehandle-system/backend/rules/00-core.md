# 团队红线

违反任意一条就停下来说明，不要「先做出来再解释」。

## 范围与准备

- 开始实现前读现有 Spec、Issue、[`project.md`](project.md) 与接口契约文档；没有文档时以当前请求为准，不额外制造文档。
- 明确本次范围、非目标与可验证结果；业务语义冲突或缺失先确认，不自行补需求。
- 修改前读目标实现、直接调用方、相关配置、同类实现与既有测试；参考实现只提供职责边界，不照搬其中的历史问题。

## 复用与最小改动

- 优先复用项目已有实现与平台能力（`utility/` 下的 config、database、connector、filter、lock、kafka、feishu、middleware）。
- 不为单次需求创建通用抽象、样板代码或未来扩展点；写代码前读 [`09-code-structure.md`](09-code-structure.md)。
- 修根因所在的共享位置；只修报告路径而同类调用继续出错，不算完成。
- 保留用户已有改动，只改需求所需范围；未获授权不 commit、push、部署或修改外部数据。
- 新增表、接口、公共包或第三方依赖前，说明现有设计为什么承载不了，并核实影响方。

## 安全与契约

- 外部输入必须校验；SQL 用参数绑定或固定白名单，不拼接不可信值。
- 密码、Token、密钥与完整敏感请求不得进入代码、配置、日志或响应。
- 动契约（字段语义、错误码、路径、proto 字段号）、动生产数据、引入新依赖、规范与存量冲突且判断不出优先级时，停下来问人。
- 改 API、库表、缓存、消息、状态语义前，核对生产者、消费者、历史数据与兼容边界；不确认就动是缺陷来源。

## 交付与验证

- 生成物不手改：`internal/dao/internal`、`model/entity`、`model/do`、`service`、`api/<模块>/<模块>.go`、`*.pb.go`。
- 改表先迁移再 `make dao`；改 api 定义后 `make ctrl` / `make service`；改 proto 后 `make proto`。
- 事务回调内不做不可撤销的副作用：Asynq、Kafka、RPC、文件上传一律移到提交之后。
- 本次新增的违规在本任务内修正；无关的存量问题只报告，不扩展成全库清理，也不据此批量重构。
- 未落地的能力按「没有」处理：见 [`project.md` 的「未落地项」](project.md#未落地项tbd禁止臆造)；TBD 契约按未定处理，不自造接口、表结构、配置项。
- 只报告实际执行的验证；失败、跳过、环境阻塞如实写明，没跑的不写成通过。提交前跑 [`make check`](README.md#硬性要求速查)。
