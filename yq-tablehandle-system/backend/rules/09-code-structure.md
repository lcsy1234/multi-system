# 方法边界与代码组织

目标是读者能看清业务，又不必为理解一件事在大量小方法间跳转。方法数量、行数、是否一行都不是质量目标；构建中的硬限制仍须满足。

## 行数区间（预警信号，不是质量目标）

| 对象 | 舒适区间 | 超出后的动作 |
|---|---|---|
| 函数体 | 20–80 行 | 超 80 行：按下面的判据拆分，或交付时写明保留理由 |
| 单个手写文件 | ≤500 行 | 超 800 行：按职责拆文件；高内聚的说明理由 |

- 行数含注释与空行；生成代码与表驱动测试不适用。
- 低于下限不合并：一行函数（如 `canPublish`）有语义价值就保留。
- **不得为凑行数拆分**：拆出的方法须满足抽取判据；压行数产生的 `doXxx` 转发层是违规。
- controller 另受硬限制：方法不超过 20 行（见 [02-api-validation.md](02-api-validation.md) 第 6 节）。

## 先划职责，再写代码

- 动手前识别本次操作的输入、不变量、副作用与输出；复杂流程先分清校验、业务决策、组装、持久化、副作用投递等实际阶段，不要求每阶段一个方法。
- 入口保留业务顺序、关键分支与副作用位置，各段处于相近抽象层级；成片字段映射、嵌套计算放进有明确结果的阶段方法。
- 命名、文件位置、import、错误与日志风格以目标模块既有规范为准；参考同类实现，不复制历史缺陷。
- 注释解释为什么与约束，不复述实现；行为变化时同步更新注释。
- 优先复用已有边界；新行为放在负责该职责的包或类型里，不为了让入口变短就新建 Helper、Context 或接口。

## 抽取的判据

抽取前能回答：**这个名字表达什么职责？调用者因此少理解了什么细节？** 满足一种实际收益即可，不要求被多处调用：

- 一个完整业务规则或阶段有清晰输入、输出与不变量，例如 `calculatePayableAmount`、`validateFactoryScope`。
- 一段实现细节打断了调用者的抽象层级，例如多字段映射、批量装载关联数据。
- 多处重复的是同一业务知识，需要统一演进；只是形状相似但变化原因不同，保持独立。
- 必须建立真实边界，例如事务代理、资源生命周期、外部协议适配；保留边界所需方法，即使实现很短。

以下内容通常留在调用点：一次 `dao.X.Save(items)`、`len(items) == 0`、简单 getter、局部 map 索引。已有 API 已说明意图时，改名转调没有收益。

- 一行也可以有价值：`canPublish` 这类业务谓词、金额精度规则；取决于语义而非行数。
- 只用一次也可以抽取：一整段计价或多字段转换，能降低阅读负担即可。
- 新方法只是搬走一条原本清楚的语句，名称是 `doXxx/handleXxx/processXxx`，且无语义或边界收益时，直接内联。

## 组装与数据流

- 一个对象的同一组业务字段在一个组装阶段完成；复用已有转换器，简单对象少量赋值留调用处。
- 索引放在使用它的阶段附近，明确重复键、缺失值与顺序语义；只有多源关联、共享规则或确实降低复杂度时才集中构建。
- 参数表达真正依赖；参数成串、多个 boolean 开关、同一可变对象穿过多层 `fill*` 时，先检查职责是否切错。
- 纯转换不隐式查库、调远程接口或写状态；有 I/O 的方法，名称与归属要让副作用可见。
- 用守卫分支降低嵌套；直观循环优于带副作用的链式调用。

## 交付前结构复查

检查本次新增和明显变长的方法，结论写在审查里，不写进代码注释：

1. 入口是否同时混入多套业务决策与大段实现细节？按完整职责抽取，而非按行数切片。
2. 每个新增方法是否真的隐藏细节、统一规则或建立边界？只是跳转就合回调用处。
3. 是否为了缩短入口新增了只转调的调用链、大而全的 Context 或通用工具？移除无收益的层。
4. 拆分前后的顺序、事务、异常、返回值与 I/O 次数是否保持？用行为测试验证，不以方法名或数量断言。

## 文档与决策记录的生命周期

代码会删，文档也要跟着收；只删代码不处理文档，等于留下会误导人的「历史真相」。

- **ADR**：决策被推翻或对应功能删除时，把原文件的状态改为
  `**Status**: superseded（YYYY-MM-DD，原因）`，**保留文件不删**；新决策用下一个编号新建。
  删除业务域时同步检查 `docs/adr/` 是否有该域的决策记录。
- **issue / spec**：关闭后在 `docs/issues/<feature>/` 保留归档，不删除；feature 整体终止时在
  `spec.md` 顶部标「已废弃」，目录保留。issue 的 `Status:` 与结论是回溯依据。
- **GLOSSARY**：删除业务域时同步删除或标注对应术语；新增业务域时补术语与 `_Avoid_`，
  不把代码里已不存在的概念留在词表里。
- 上述三条由 `TestDocsLifecycleADR` / `TestDocsLifecycleGlossary` / `TestDocsLifecycleIssues` 检查。
- **联动清单**：删除业务域/重命名公共包时，按顺序核对
  `rules/` → `README.md` → `AGENTS.md` → `docs/`（ADR / issues / agents）→ `GLOSSARY.md`
  → 迁移 → `internal/consts`；元守卫 `TestMetaDocsReferences` / `TestMetaRuleGuardsExist`
  必须通过。
